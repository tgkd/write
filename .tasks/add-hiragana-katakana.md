# Task: Add hiragana and katakana practice to Write

## Goal
The app offers the standard kana (hiragana and katakana, 71 each: the basic 46 plus the 25
dakuten/handakuten forms) alongside the kanji. Kana appear in the picker grid, can be filtered with
new "Hiragana" and "Katakana" pills, can be found by romaji search ("ka" finds か and カ), can be
started as a random practice session, and show their romaji where a kanji shows readings. Stroke
practice and validation work for them unchanged.

## Context
- SwiftUI app, iOS 16 deployment target, Swift 6.0, XcodeGen. `project.yml` is the source of
  truth; `Write.xcodeproj` is generated by `xcodegen generate` and IS committed, so the regenerated
  `project.pbxproj` belongs in the change. Never edit the `.xcodeproj` by hand.
- Stroke data comes from `Write/Resources/kanji_strokes.json`. It is a JSON object keyed by
  lowercase hex code point with no leading zeros (e.g. `"4eee"`, `"5c71"`). Each value has
  `codePoint`, `element`, `strokes` (`strokeNumber`, `pathData`, `strokeType`), `components`, and
  the optional KANJIDIC2 fields `onYomi`, `kunYomi`, `meanings`, `grade`, `jlpt`, `freq`.
- The JSON is produced by `Scripts/preprocess_kanjivg.py` from `Data/kanjivg.xml` and
  `Data/kanjidic2.xml`. `Data/` is gitignored but present in this checkout. The download commands
  are in `README.md` if it is ever missing. Run on the current `Data/` files, the unmodified script
  reproduces the committed JSON byte for byte (verified). So after this change the JSON diff must
  consist ONLY of added kana entries. Any change to an existing kanji entry means something is
  wrong.
- The script currently drops everything outside CJK Unified Ideographs via `is_cjk_unified`
  (U+4E00–9FFF, U+3400–4DBF). KanjiVG does contain kana: all 142 target characters are present in
  `Data/kanjivg.xml` (verified), in the same 109×109 coordinate space as the kanji. So the
  validation pipeline (`Engine/`) and `StrokeRenderer` need no changes. KANJIDIC2 and
  `Scripts/jlpt_levels.json` contain no kana, so kana entries get no readings, meanings, grade,
  jlpt or freq.
- `KanjiDataStore` decodes the JSON into `[String: KanjiData]`. `allCodePoints` is
  `keys.sorted()`, a string sort. Kana code points (`3042`…`30dd`) sort before every kanji
  (`3400`+), so under "All" the kana appear first in the grid. That is intended.
  - `search(query:)` matches `meanings` (lowercased contains) and `onYomi`/`kunYomi` (contains).
  - `randomKanji(jlpt:count:)` is called ONLY from `KanjiPickerView.sessionButton`.
- `KanjiPickerView` holds `@State private var selectedJLPT: Int?`. The filter bar shows "All" plus
  N5…N1 pills built by `filterPill(label:level:)`, and filters `displayedKanji` and the random
  session by it. Typing a character into search already goes through `lookup(character:)`, so
  typing か works as soon as the data exists.
- Readings are displayed in five places, each reading `onYomi` / `kunYomi` / `meanings` directly:
  - `PracticeView.kanjiHeader`
  - `iPadPracticeView.readingsBlock`
  - `KanjiDetailView.readingsBlock`
  - `NotebookHeaderView.configure(with:)`, which builds `readingsLabel.text` from parts
  - `SessionSummaryView`, which shows `meanings.prefix(2)`
  For kana all of those are nil, so without a change a kana shows no text at all.
- `PreprocessingTests` loads the real bundled JSON; `KanjiDataStoreTests` builds its store from an
  inline dictionary via `KanjiDataStore(data:)`. `KanjiDataStoreTests.testCount` asserts exactly 2
  entries, so new fixtures go in a new test file rather than that fixture.
- Baseline: the full suite passes, 164 tests, 0 failures, with the Acceptance test command.

## Plan
1. Create `Scripts/kana_romaji.json`: a flat JSON object mapping each lowercase hex code point to
   its Hepburn romaji, 142 entries. Hiragana, in this order, with the romaji list aligned
   one-to-one:
   `あいうえおかきくけこさしすせそたちつてとなにぬねのはひふへほまみむめもやゆよらりるれろわをんがぎぐげござじずぜぞだぢづでどばびぶべぼぱぴぷぺぽ`
   → `a i u e o ka ki ku ke ko sa shi su se so ta chi tsu te to na ni nu ne no ha hi fu he ho ma
   mi mu me mo ya yu yo ra ri ru re ro wa wo n ga gi gu ge go za ji zu ze zo da ji zu de do ba bi
   bu be bo pa pi pu pe po`.
   Katakana are the same characters shifted by +0x60 (ア = あ + 0x60) with the same romaji. No
   small kana, no ゐゑヰヱ, no ゔヴヷヸヹヺ, no iteration marks, no ー.
2. `Scripts/preprocess_kanjivg.py`: load `kana_romaji.json` from the script's own directory, the
   same way `jlpt_levels.json` is loaded.
   - An entry passes the filter if `is_cjk_unified` OR its code point is a key of the kana map.
   - Kana entries get `"romaji": <value>` and no KANJIDIC2/JLPT merge. Their lookups would find
     nothing anyway, but skip them explicitly.
   - After the loop, exit non-zero with a message naming the missing characters if any kana-map
     key was not produced. The kana set is a contract, not best-effort.
   - Update the final summary print to report kanji and kana counts separately, and update the
     module docstring's first paragraph to mention kana. It is an existing docstring; keep the
     rest of it.
3. Regenerate the data:
   `python3 Scripts/preprocess_kanjivg.py Data/kanjivg.xml Data/kanjidic2.xml Write/Resources/kanji_strokes.json`.
4. `Write/Models/WritingScript.swift`: `enum WritingScript: Sendable { case kanji, hiragana,
   katakana }` with `init(codePoint: String)`. Map U+3041–309F → hiragana, U+30A0–30FF →
   katakana, anything else → kanji.
5. `Write/Models/KanjiData.swift`: add `var romaji: String? = nil` after `freq`, same style as the
   other optionals so the existing JSON and test fixtures keep decoding. Add
   `var script: WritingScript { WritingScript(codePoint: codePoint) }`. Keep the type name
   `KanjiData`; renaming it is out of scope.
6. `Write/Models/CharacterFilter.swift`: `enum CharacterFilter: Hashable, Sendable` with cases
   `all`, `hiragana`, `katakana`, `jlpt(Int)`, plus:
   - `var label: String`: "All", "Hiragana", "Katakana", "N\(level)".
   - `func includes(_ kanji: KanjiData) -> Bool`:
     - `all` → true;
     - `hiragana` / `katakana` → `kanji.script` matches;
     - `jlpt(n)` → `kanji.jlpt == n`.
   - `static let pickerOrder: [CharacterFilter] = [.all, .hiragana, .katakana, .jlpt(5),
     .jlpt(4), .jlpt(3), .jlpt(2), .jlpt(1)]`.
7. `Write/Services/KanjiDataStore.swift`:
   - Replace `randomKanji(jlpt:count:)` with `randomCharacters(matching filter: CharacterFilter,
     count: Int) -> [KanjiData]`: the same shuffle-and-prefix, filtered by `filter.includes`.
   - In `search(query:)`, also match when `kanji.romaji?.lowercased() == q`. Use exact equality,
     not contains, so "ka" does not match "kya"-style strings or every romaji containing "a".
8. `Write/Views/KanjiPickerView.swift`:
   - Replace `selectedJLPT: Int?` with `selectedFilter: CharacterFilter = .all`.
   - Delete the `jlptLevels` constant.
   - The filter bar iterates `CharacterFilter.pickerOrder`.
   - `filterPill` takes a `CharacterFilter`; its selected styling and animation are unchanged.
   - `displayedKanji` filters with `selectedFilter.includes`; `sessionButton` calls
     `randomCharacters(matching: selectedFilter, count:)`.
   - Change the search prompt to "Search kanji or kana".
9. Reading displays: in each of the five places listed in Context, when `romaji` is non-nil show
   it in the slot the readings occupy.
   - Use the font/style of that view's on'yomi line (`PracticeView`, `iPadPracticeView`,
     `KanjiDetailView`).
   - In `NotebookHeaderView`, add it as the first element of `parts`.
   - In `SessionSummaryView`, show it where `meanings` would be, with the same font.
   Kanji rendering must be unchanged.
10. Tests:
    - `WriteTests/CharacterFilterTests.swift`: build a store from an inline dictionary holding one
      kanji with `jlpt: 5`, one hiragana (`"304b"`, か, `romaji: "ka"`), one katakana (`"30ab"`,
      カ, `romaji: "ka"`), each with one minimal stroke, mirroring `makeTestJSON` in
      `KanjiDataStoreTests`. Assert:
      - `WritingScript(codePoint:)` classifies all three;
      - `includes` for every `pickerOrder` case against each entry;
      - `search(query: "ka")` and `search(query: "KA")` return both kana and not the kanji
        (give it a meaning without "ka");
      - `randomCharacters(matching: .hiragana, count: 5)` returns only か.
    - `WriteTests/PreprocessingTests.swift`: add tests that the bundled data has exactly 71
      hiragana and 71 katakana (by `script`), that every kana has a non-empty `romaji` and a nil
      `jlpt`, that あ (`"3042"`) has 3 strokes with romaji "a", and that ア (`"30a2"`) has 2
      strokes. Keep the existing kanji-count test (it is `> 6000` and still holds).
11. Run `xcodegen generate` so the new Swift files are in the committed project.
